01 研究背景

企业文档管理中的"知识孤岛"困境

核心痛点

  • 文档分散存储，缺乏统一管理平台
  • 关键词检索无法理解语义关联
  • 大模型直接问答存在幻觉与上下文窗口限制
  • 多模态内容（图片/音频/视频）被排除在检索体系之外

RAG 技术的应对

"检索增强生成将信息检索与大语言模型结合 — 先从外部知识库检索相关内容，再作为上下文提供给模型，从根本上降低幻觉出现的概率。"

02 技术路线

知识图谱增强RAG — GraphRAG vs LightRAG

GraphRAG

  • 5步索引：切块 → 实体/关系抽取 → 摘要合成 → Leiden 社区检测 → 社区报告生成
  • Global Search：Map-Reduce遍历社区摘要，预计算层次化全局知识视图
  • 优势：深度全局洞察力强，实体消歧策略完备，多跳推理精度高，可解释性强
  • 代价： Token 消耗数十倍于传统 RAG ，增量更新牵一发而动全身， Global Search 延迟可达分钟级

LightRAG

  • 3步索引：切块 → 实体/关系(+关键词)抽取 → 键值对去重
  • 低层检索：用具体实体名匹配节点 → 一跳邻居扩展 → 收集关联关系与文本块
  • 高层检索：用抽象主题关键词匹配关系边 → 聚合涉及的实体与语义上下文
  • 优势： Token 减少99%，增量仅追加节点/边，秒级响应
  • 代价：全局深度洞察弱于 GraphRAG ，实体消歧仅基于名称匹配，不处理时效冲突

本文选型依据：系统面向企业知识库，文档更新频率高、数据规模中等，要求实时交互。LightRAG 的"按需检索 + 增量友好"设计更适合轻量化场景 — 无需社区重建，新文档直接追加，查询响应在秒级。避免 GraphRAG 的"Token 焚烧炉"索引成本和分钟级 Global Search 延迟。

ChunkEntity 双向索引 — 知识图谱检索的通用优化

问题

知识图谱实体与文档切片之间缺乏双向索引——实体搜索找到了实体，却无法定位"哪些 chunk 包含这个实体"；纯文本尚可依赖语义兜底，图片走视觉理解得到的信息则几乎检索不到

流程

上传遍历每个 chunk → 字符串匹配实体名称 → 批量插入 (chunkId, entityId) → skipDuplicates 去重，纯文本和图片文本走同一逻辑

方案

新增 ChunkEntity [chunkId, entityId] 多对多关联表，充当向量存储层与知识图谱层之间的通用索引桥梁

效果

知识图谱匹配实体 → 即时查出关联 chunk → 填补"由实体找文档"的反向通路，纯文本和多模态文档统一受益

05 评估实验

数据集构建与评估指标

数据集

  • 5份医疗/药学文档，共107,000字
  • 100对问答：事实型43 · 推理型33 · 比较型24
  • 12对跨文档综合问题
  • 切片大小=2500词元

三项评估指标

  • Recall@K — Top-K是否命中正确chunk
  • NDCG@K — 命中位置的质量加权
  • MRR — 首个正确答案排名的倒数均值

  • 知识图谱辅助检索：知识图谱路径候选chunk + 向量余弦排序（排序方式一致，差异唯一归因于知识图谱路径贡献）

指标解读

  • R@1 55.50%：过半查询在首个结果即命中，2500 词元细粒度下排序精度可接受
  • R@5 93.50%：Top-5近乎全覆盖，答案信息未丢失，问题在于排序精度而非检索能力
  • MRR 75.83%：首个正确答案平均排在1.3位，排序稳定性良好

题型差异分析

  • 推理型最优：因果机制段落语义密度高， embedding 对因果逻辑编码能力强
  • 事实型稳健：数值/定义在细粒度 chunk 中信息完整性有所损失，但仍可Top-3覆盖
  • 比较型最弱：对比双方被切分至不同 chunk ，单一向量无法聚合跨 chunk 的分散信息

关键发现

  • 知识图谱辅助检索全面超越 baseline ：三项指标均有提升，R@5 +8.34pp 最为显著
  • 跨文档实体链接：通过实体关系网络发现跨文档关联实体，自动扩展查询范围
  • 消融设计保证归因：两配置仅在检索路径上不同（排序方式一致），差异唯一归因于知识图谱贡献
  • 规模化潜力：随着文档规模和跨文档查询比例增加，知识图谱相对优势有望进一步扩大

05 实验结果

Chunk粒度消融 — 7500 vs 2500 词元

同一评估集 · text-embedding-v4 · 余弦相似度排序

指标chunk=7500chunk=2500变化
R@180.68%55.50%−25.18pp
R@396.59%90.00%−6.59pp
R@598.86%93.50%−5.36pp
MRR88.74%75.83%−12.91pp

核心机制：答案信息的完整性分散

  • R@1 骤降 −25.18pp vs R@5 仅降 −5.36pp：降幅严重不对称，说明答案信息并未丢失，而是被分散
  • 大 chunk (7500)的"虚高"：高R@1并非检索模型精确排序所致，而是 chunk 覆盖范围过大、评估分辨率不足——好比撒网范围太大，无论鱼在哪都被一并罩住，并非捕鱼技术好
  • 小 chunk (2500)的真实考验：完整答案被切分至2–3个 chunk ，单一向量匹配强度下降，但放宽至Top-5即可重新覆盖

粒度权衡与评估定位

  • 大 chunk 利于答案完整匹配，但混入大量无关信息，生成环节引入噪声
  • 小 chunk 利于精确定位与溯源，但拆散知识单元，对排序模型提出更高要求
  • 本次评估选择 2500 词元：更真实衡量排序能力，贴近企业知识库实际场景

06 总结

主要工作

  1. 1 完成多模态RAG问答系统的全栈工程实现 — Next.js 15 + PostgreSQL配合 pgvector 实现向量存储，文本/图像/音频三模态支持，串联外部模型 API 调用工作流
  2. 2 引入 LightRAG 双层知识图谱扩展 + 构建可视化的实体、关系网络知识图谱
  3. 3 定制化多模态知识库问答的语义检索链路，引入自适应检索路由匹配、多模态实体链接等机制
  4. 4 构建轻量化的医疗文档问答集，并对原型系统 RAG 模块进行消融实验测试
  5. 5 分析消融实验结果，分析各项评估指标的数值大小与变化趋势，从实践角度真正理解了 RAG 系统的性能与局限性
  6. 6 实现 MCP 客户端框架，支持多服务器并行接入与 Function Calling 自主调用
  7. 7 构建 Jest 双模式测试框架，覆盖全部模块功能领域

06 展望

未来改进方向

  • 全模态深化 — 视频关键帧提取与描述生成，将视频内容纳入可检索范围；优化跨模态数据处理流程，确保不同模态间信息传递与融合的高效准确，构建真正的全模态 RAG
  • 知识图谱多跳推理 — 引入图神经网络或路径排序算法实现多跳关系推理（如" A 产品→ B 公司→收购 C 公司"跨步关联）；探索时序知识图谱追踪实体关系动态演化
  • 领域适配 — 通过垂直领域语料继续预训练或微调，提升嵌入模型对专业术语的语义捕捉精度；扩展更多领域更大规模问答集，全面衡量泛化能力
  • 性能扩展 — 引入向量索引加速技术以亚线性复杂度替代暴力检索；向量数据库与关系型数据库分离部署按需独立扩缩容；高频知识库增加缓存层降低重复开销
  • Agent 自主工作流 — 引入智能体框架，使系统自动分解复杂需求为多步骤执行计划，自主完成文档检索、信息抽取、结构化汇总和报告生成全流程
